SecureBench presentation

Benchmarking agents without giving them the benchmark.

A practical security architecture for running coding benchmarks with public workspaces, hidden answers, and containerized execution.

Public task data Evaluation inputs Hidden scorer data Benchmark runtime image
Agent seesinstructions, public files, task.json
Test sandbox seescandidate output plus private test inputs
Only evaluator seesgold patch, answers, rubrics, expected state
High-level idea

Three boundaries, one benchmark run.

01

Data visibility

Every task field becomes public, evaluation-only, or hidden before anything runs.

02

Containerized harness

The agent or command runs inside the benchmark image, not on the host.

03

Fresh evaluation

The candidate is scored in a separate sandbox with hidden data still evaluator-side.

Security goal: the tested agent can solve the public task, but cannot tamper with or read the grading machinery.

What changes

SWE-bench vs SecureBench.

Normal SWE-bench patch-first

InputDataset instance + prompt.
Candidate productionLeft to external model runner or agent setup.
EvaluationDockerized patch application and tests.
Missing boundaryNo standard public/eval/hidden split for the agent runtime.

SecureBench run-first

InputSame task, normalized into visibility-labeled resources.
Candidate productionAgent runs in the benchmark image with public data only.
EvaluationFresh verifier sandbox receives candidate + eval inputs.
Added boundaryHidden tests, gold patch, and scorer files never enter the agent workspace.
Threat model

What we are protecting.

01Agent cannot read hidden answers or gold patches.
02Agent cannot edit verifier files before scoring.
03Harness runs in Docker, not as an unrestricted host process.
04Result records redact hidden values.
The benchmark owns the task. The tester owns the harness. SecureBench owns the boundary.
