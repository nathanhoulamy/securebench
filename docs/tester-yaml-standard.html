SecureBench Tester YAML Standard

A small execution file for benchmark testers. It selects a benchmark pack and candidate-producing harness without changing the benchmark security contract.

Benchmark-owned: task/runtime requirements Tester-owned: harness and output dir SecureBench-owned: isolation and evaluation Harness config cannot relax benchmark security
Open Revised Standard Open Revised Examples

Purpose

The tester YAML describes one execution of a benchmark pack. It is separate from the benchmark manifest and benchmark rows. The benchmark defines task requirements and security constraints; the tester YAML chooses the tested harness, output location, and required credentials.

schema_version: "0.2"

run:
  id: repo-repair-codex
  output_dir: runs/repo-repair-codex

benchmark:
  manifest: ./benchmarks/repo-repair/manifest.yaml
  tasks: ./benchmarks/repo-repair/tasks.jsonl

verification:
  disallow_dangerous_commands: true
  deny_commands: []

harness:
  type: codex
  config:
    model: gpt-5.4-mini
    version: latest
    task_file: task.json
    timeout_seconds: 900
    allow_external_tools: false
    allowed_domains:
      - docs.python.org
Tester YAML cannot expose hidden benchmark data to the harness. Verifier dangerous-command policy is fail-closed and can only activate known benchmark-declared verifier needs.

Harness Execution

command

SecureBench runs the tester-provided command inside the benchmark environment image with only public workspace data, allowlisted credentials, and optional domain allowlisted egress.

codex

SecureBench runs Codex inside the benchmark environment image and mounts a read-only cached tooling overlay plus fresh per-row agent state. Provider API traffic goes through a SecureBench relay that keeps the real API key outside the agent container.

claude_code

SecureBench runs Claude Code inside the benchmark environment image and mounts a read-only cached tooling overlay plus fresh per-row agent state. Provider API traffic goes through a SecureBench relay that keeps the real API key or subscription token outside the agent container.

Network controls: allowed_domains controls generic agent-container egress, not provider-hosted web search. Provider-hosted external tools stay blocked unless allow_external_tools: true is set. Claude Code allowed_domains relies on the CLI honoring its documented NO_PROXY behavior so provider relay traffic bypasses the generic egress proxy.
# Codex tooling overlay
harness:
  type: codex
  config:
    model: gpt-5.4-mini
    allow_external_tools: false
    allowed_domains:
      - docs.python.org

# Claude Code subscription
harness:
  type: claude_code
  config:
    auth: subscription
    model: sonnet

# Containerized command harness
harness:
  type: command
  env:
    - CUSTOM_API_KEY
  config:
    command: ["python", "-m", "my_harness"]
    allowed_domains:
      - pypi.org

Harness Types

Supported and Planned Types

Common harnesses should not expose raw commands. SecureBench owns the adapter behavior.

Agent-agnostic execution
TypeStatusMeaning
codeximplementedRun the Codex CLI harness inside the benchmark environment image with a read-only mounted tooling overlay.
claude_codeimplementedRun the Claude Code harness inside the benchmark environment image with a read-only mounted tooling overlay.
commandimplementedContainerized custom command harness for tests and advanced harness integration.
acpfuturePotential future adapter where SecureBench acts as an Agent Client Protocol client.
Installation policy: SecureBench should not install third-party harnesses inside benchmark containers by default. Named agent harnesses prepare a reusable read-only CLI overlay outside the benchmark run and mount fresh writable agent state per row. SecureBench checks availability, versions when possible, required env vars, and whether the benchmark constraints can be satisfied.
